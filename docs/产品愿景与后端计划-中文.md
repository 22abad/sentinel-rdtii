# 产品愿景 整合 + 后端准备工作分步计划（中文）

> 目标：把 Dong 想讲的产品愿景（工作人员点点拖拖完成工作、每步有记录、素材入库避免重复劳动）
> 整合成一套连贯的叙事，并列出**后端**要做的准备工作，分阶段。
> **前端由队友做，本文只规划后端。** 每条都标了「✅已有 / 🟡半成品 / 🔴待建」。

---

## 一、产品愿景（一句话 + 三大卖点）

**一句话**：把"人工读法律、映射指标、打分"的苦活，变成一个**可视化、可复用、可审计**的工作台——
新人拖几个积木、点几下，就能产出带证据的评估结果；干过的活自动入库，越用越省力。

三大卖点（路演时说这三点）：
1. **点点拖拖就能干活**：拖拽式节点画布，非技术人员也能搭一条"发现→抽取→打分→导出"的流水线。
2. **每一步都有记录**：谁、什么时候、对哪份文件、做了什么、结果如何——全程留痕，可回溯、可复现、可审计。
3. **素材入库、避免重复劳动**：处理过的法律文本按内容指纹入库，下次遇到同一份**直接复用不重跑**；积累的语料成为团队越来越厚的"知识底座"。

## 三、后端准备工作 · 分 4 步（Phase 0–3）

> 说明：每步都标了「后端(我们做) vs 前端(队友做)」。前端只调我们提供的 API。

### Phase 0 — 现状核实 + 打通（0.5–1 天）  ✅ 已实测完成
**目的**：先把已有的画布/入库/审计端到端跑通一遍，确认真实缺口（避免凭空造）。

**实测结果（2026-07-15，postgres 起于 docker，直接从 0 跑）：**

| 验证项 | 结果 |
|---|---|
| **素材入库去重**（避免重复劳动的核心） | ✅ **通过**。同一份内容上传两次 → 第二次 `deduplicated=True`、复用同一 doc、不重跑 |
| **知识底座已积累** | ✅ 数据库里已有 **444 份文档、443 已处理、57,516 个可检索文本块**（带向量）——底座真实且很大 |
| **节点真能执行**（点点拖拖能干活） | ✅ `extract.mappings` 节点跑通，产出 2 条映射（指标 6.4 + 逐字引文），status=success |
| 已有节点积木 | 🟡 4 个：`discovery.search`、`source.fetch_text`、`extract.mappings`、`rag.query` |

**核实出的真实缺口（下面几个 Phase 的依据）：**
1. 🔴 **无通用"活动/操作历史"表**——只有复核专用的 `audit_trail` 和发现源的 `discovery_source_audit_events`。→ Phase 1 成立。
2. 🔴 **抽取结果没落库**（`regulation_mappings` 现 0 条）——CLI 只写 CSV 文件，结果没进库供复用/复核。→ Phase 2 相关。
3. 🟡 **打分和导出其实已有，只是没做成独立拖拽节点**（更正 Phase 0 初判）：
   - **打分不缺**——抽取节点输出里已带 `score / raw_score / Cat_Score`（确定性程序算的）；前端 audit 画布的 **preview 显示的就是这个分数**。
   - **Excel 导出不缺**——`/api/excel/export` API 已有（openpyxl 生成）。
   - 所以 Phase 3 的"补节点"从🔴降级为🟡**可选**：核心流水线（发现→抓取→抽取[含打分]→复核preview→导出）实测已能端到端跑，独立的打分/导出积木可有可无。

**结论**：愿景的地基（入库去重 + 知识底座 + 节点执行 + 打分 + 导出）**实测都在**，真正要补的其实只有**两块**：①通用操作历史（Phase 1）②抽取结果落库以支撑跨会话复用/复核（Phase 2）。Phase 3 降为可选打磨。

### Phase 1 — 「每一步都有记录」：活动审计持久化  ✅ 已完成（实测通过）
**缺口**：原来成本审计在内存、canvas 存布局、review 有留痕，但缺一张**统一的"活动历史"表**。**已建好并跑通：**
- ✅ 后端：`activity_log` 表（user_id、action、target_type/id、economy、status、summary、detail(JSONB)、时间）——已进 `init.sql` + 运行库。
- ✅ 后端：`services/activity_log.py`（`record_activity` 记录 + `list_activity` 查询,best-effort 不会因记日志失败而中断真活)。
- ✅ 后端：**入库自动记一条 ingest 活动**（`canvas_file_ingest` 已接）；`record_activity` 供 extract/discover/review/export 调用。
- ✅ 后端：`GET /api/activity`（按 user/文档/动作/时间查,支持分页）——实测 HTTP 200、过滤生效。
- ✅ 测试:4 个新单测(端点/过滤/优雅降级/状态校验),535 全绿。
- **前端可直接挂"操作历史/时间线"面板,调 `GET /api/activity`。**（前端队友做）
- ✅ 已扩展覆盖:`record_activity` 现已接入 **ingest / extract / discover / export**(网页 API 路径),操作历史更完整。
- 待办(可选):`GET /api/activity/{id}` 单步详情;review 端点也补一条。

### Phase 2 — 「素材入库、避免重复劳动」：复用底座打通  ✅ 结果层已完成（实测通过）
**现状**：上传的文件已按指纹去重、进了 `documents`+向量库（文档层复用）。
**已补齐结果层复用（抽取结果落库 + 复核晋级 + 去重复用）：**
- ✅ 后端：新建 `verified_evidence` 表（economy/indicator/law/quote/article/source/score/review_status），**按 (经济体+指标+归一化法名+引文哈希) DB 级唯一去重**——同一条证据永不重复入库。（进 init.sql + 运行库）
- ✅ 后端：`services/evidence_store.py`：`save_evidence`(存,自动去重) + `find_evidence`(查/复用) + `set_review_status`(draft→approved/rejected 晋级)。best-effort,无 DB 也不崩。每次落库/晋级都记一条活动日志(接 Phase 1)。
- ✅ 后端：API `POST /api/evidence`(存)、`GET /api/evidence`(查/复用源)、`POST /api/evidence/{id}/review`(晋级)。实测全链路:存→再存全去重→查→approved→可复用。
- ✅ 测试:4 个新单测(端点/去重/跳过不完整/无DB降级),539 全绿。
- 待办(可选,决赛阶段):让**发现/抽取流水线开跑前先查 `find_evidence` 命中即复用**(现在存了、可查、可复用,但自动"命中即跳过重抽"还没接进 CLI——因为判委 CLI 要保持免数据库,这块更适合放网页/API 路径)。

### Phase 3 — 「点点拖拖」：全流程节点化 + 工作流保存/回放（2–3 天）
**现状**：有画布 + 部分节点 + 节点流式执行。
**缺口**：确保**整条流水线都能当积木拖**，且能把一条搭好的流水线**存成命名工作流、一键回放**。
- 🟡 后端：补齐缺失的节点执行器（发现/抓取/打分/导出，凡是命令行能做的都要有对应节点）。
- 🔴 后端：`POST /api/workflows`（存一条命名工作流）、`POST /api/workflows/{id}/run/stream`（回放，流式返回进度）。
- 🔧 后端：节点执行统一走 Phase 1 的活动日志 + Phase 2 的复用库。
- 产出：新人拖一条流水线、存下来、下次一键重跑——这就是"点点拖拖完成工作"。

## 四、路演叙事（把三点串成一个故事，照着说）

> 场景化，别念功能表。

"想象一位新入职的研究员。**过去**，她要打开十几个政府网站，手动翻上百页法律，一条条抄、一条条判、一条条打分——几天做一个国家，而且下次还得重来。

**用我们的工具**：她在画布上把'发现→抽取→打分→导出'几个积木一拖，点运行——屏幕上实时进度条告诉她读到哪部法、抽到第几篇。产出的每一行都带**逐字原文引文**,分数由程序算、可审计。

而且她做的每一步都被**记录下来**:谁、什么时候、对哪份文件、得到什么结果——随时可回看、可复现。

最妙的是:她处理过的每一份法律都**入了库**。下次她或同事再遇到同一份,系统直接复用——**干过的活不白干,团队的知识底座越用越厚**。

我们把'人肉苦活'变成了'可视化、可复用、可审计'的流水线。"

**一句话金句**："Point, drag, run — and never do the same work twice."

## 五、总时间估（后端准备工作）

| 阶段 | 内容 | 估时 |
|---|---|---|
| Phase 0 | 现状核实 + 打通冒烟 | 0.5–1 天 |
| Phase 1 | 活动审计持久化 + 历史 API | 1–2 天 |
| Phase 2 | 素材复用底座打通 | 2–3 天 |
| Phase 3 | 全流程节点化 + 工作流保存/回放 | 2–3 天 |
| **合计** | | **约 6–9 天**（后端 1 人） |

**优先级建议**（如果时间紧）：
- 路演/演示要"讲得出、演得动" → **Phase 1（每步记录)** 最出彩、最好演,先做。
- "避免重复劳动"是差异化卖点 → **Phase 2** 第二。
- Phase 3 是完整体验,可作为决赛阶段目标。

> ⚠️ 严谨提醒：Phase 0 先跑通再动手,避免我们对"缺口"的判断有偏差（本文的🔴待建项都需 Phase 0 核实后再最终确认工作量）。前端契约（API 字段）在每个 Phase 动手前先和队友对齐一次。
